# 取り込み（初回）

既存プロジェクトの情報源を集めて突き合わせ、bantoの台帳（`banto/` 配下のMD）と判断票を作る。
**どれが正かは決めない。** 食い違いはすべて判断票にして、人に渡す。

## 実行のしかた

```
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/banto.py" --project <対象プロジェクト> <コマンド>
```

Windows では `python3` を `python` に置き換える。openpyxl が無いと言われたら `pip install openpyxl`。
以下、この呼び出しを `banto <コマンド>` と書く。

## 手順

1. **対象と状態を確かめる**：対象プロジェクトのルートを確認する。Gitで管理され、作業ツリーがきれいかを見る。管理されていなければ、取り込みの前に現状をコミットしてよいか聞く（取り込み結果と元の状態を比べられるようにするため）。
2. **情報源を棚卸しする**：次を探し、見つけたものを一覧にしてユーザーに見せる。
   - テーブル定義：設計書（MDの表、Excelの「テーブル: 名前」＋「カラム / 型 / 制約」表）、DDL（`schema.sql`、マイグレーション）、ORMのエンティティ（JPA）
   - テスト：テスト仕様書・報告書（MDの「テストメソッド」表）、テストコード（JUnit 5）、実行結果（surefire の `TEST-*.xml`）
   - 設計書が「対象範囲」を自分で書いていれば、その一文を控える（`scope_note` に入れる）
3. **含める情報源を決めてもらう**：何を含め、何を外すかはユーザーが決める。v0.1 で読めない種類（例：Flyway の差分マイグレーション、Python の ORM）は、読めないと正直に伝える。
4. **`banto/sources.json` を書く**：形式は `${CLAUDE_PLUGIN_ROOT}/docs/spec.md` の「情報源の一覧」。`id` は短い英字、`label` は判断票に出る日本語名。
5. **同期する**：`banto sync`。出力の件数を報告する。
6. **結果を渡す**：`banto/drifts/README.md`（グループ別の一覧）を開き、重要度の高いグループから要点を3〜5行で伝える。次は `/banto:decision-sheet` で判断に進むことを示す。

## 意味の推定が要るとき

注釈やDDLに書かれていない事実（Validatorクラスでの必須チェック、サービス層の桁数制限など）は、スクリプトでは拾えない。
必要なら `extractor` エージェントに調べさせる。推定した内容は台帳の値には入れず、判断票や台帳の「メモ」「補足」に **（推定）** と明記して残す。

## 防ぐ失敗

設計書・DDL・コードを人が目で突き合わせ、見落としたまま「設計書どおり」として納品する。

例：設計書・H2・MySQLは `VARCHAR(20)` なのに、PostgreSQLだけ `TEXT`、エンティティは `@Pattern(\d{10})` で10桁固定。目視では見落とすが、取り込みで1枚の判断票に並ぶ。

## やらないこと

- 判断しない。「多数派がこうだから」と台帳の値を決めない
- 情報源のファイルを書き換えない（取り込みは読むだけ）
