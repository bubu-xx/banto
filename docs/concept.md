# banto 構想

## 解決したい問題

- **どれが正か問題**：設計書とコード、Excelの設計書同士、仕様と実装が食い違ったとき、どれが正しいのか誰にも分からない。結局、声の大きい側や、たまたま開いた資料が正になる。
- **Excelでは関係が見えない**：各文書の中身は読めても、「この設計はどの要件から来て、どのコードとテストにつながっているか」が見えない。ずれが起きても影響の範囲が分からない。

## 中心の考え方

1. **MDが関係のすべてを持つ**：要件・基本設計・詳細設計・ソースコード・テスト（仕様と結果）の中身と、それらのつながりをMDで完全に管理する。
2. **MDの記述は実物と一致していなければならない**：MDは各工程の実物（コード、DB、テスト結果など）と常に一致している状態を目指す。
3. **ずれは判断の材料として差し出す**：ずれを見つけたら、どちらが正かをbantoは決めない。判断に必要な材料を揃えて人に見せる。
4. **人の判断と理由を記録する**：決めた内容と理由をMDに残す。次に同じ箇所でずれが起きたとき、過去の判断が材料になる。

この仕組みの魅力は、**完璧に管理されたMDがあるから、何をどう直すかを人が判断できる**ことにある。

## 管理する範囲

要件 → 基本設計 → 詳細設計 → ソースコード → テスト（仕様と結果）

- 文書の原本はMD。Excelは提出用の写しで、直接編集しない。
- ソースコードやDBは、それ自体が実物。MDはそれらとの対応を持つ。

## 一致の3種類

| 種類 | 例 | 確かめ方 |
|---|---|---|
| 構造の一致 | テーブル定義書とDB、API設計とルーティング、テストケース一覧とテストコード | スクリプトで機械的に照合する |
| 意味の一致 | 詳細設計の処理内容とコードの実装、要件と設計の対応 | AIが判定し、人が確認済みにする |
| 結果の一致 | テスト結果の報告とCIの実行結果 | 実行ログから取り込む |

## 2つの場面、1つの仕組み

### 取り込み時（既存プロジェクトから最初のMDを作る）

既存プロジェクトには、同じ事柄について複数の情報源がある（既存のExcel設計書、DB、コード、テスト、チケット）。
項目単位で突き合わせ、次の3つに仕分ける。

- **一致**：そのままMDに入れ、出どころを記録する
- **片方にしかない**：設計書にあってコードにない、コードにあって設計書にない
- **食い違い**：両方にあるが内容が違う

後の2つは判断票にして人が判断する。**完璧なMD＝未判断のずれがゼロ**の状態。

### 運用中（変更のたびに）

変更があるたびに一致検査をかけ、ずれを判断票にする。レビューの指摘も「人が見つけたずれ」として同じ流れに乗せる。

## 判断票

1件のずれについて、次を揃えて見せる。

1. **何がずれているか**：MDの記述と実物を並べる
2. **つながり**：上流（どの要件・設計から来たか）と下流（どのコード・テストに影響するか）
3. **経緯**：どちらが、いつ、なぜ変わったか（コミット、レビューの指摘、過去の判断）
4. **選択肢と影響**：「MDを直す」「実物を直す」それぞれで、ほかに何を直す必要が出るか

### 量への対処

古いシステムの取り込みでは、ずれが数百〜数千件になり得る。

- **一括判断**：「このテーブル群の列の型はDBを正とする」のように、同じ種類のずれをまとめて判断できる。一括判断も、誰がどの規則で決めたかを記録する
- **重要度で並べる**：業務ロジックに関わるずれを先に、表記揺れは後に
- **グループ化**：同じ原因から来たずれをまとめて見せる

## Excel清書とレビュー往復

- MDからExcelへは一方向。Excelは直接編集しない
- Excelには非表示列で元のMDとIDを埋め込み、指摘を逆引きできるようにする
- 清書と同時に空のレビュー表を出す。指摘は行番号ではなくIDで指す
- 記入済みのレビュー表を取り込み、指摘を判断票の流れに乗せる

## 構成

### Skill（作業の手順）

プラグインとして入れると `/banto:<名前>` で呼べる。

| Skill | 用途 |
|---|---|
| `import` | 既存プロジェクトの取り込みと突合せ（初回） |
| `check-drift` | 運用中のずれの検出（同期と整合検査） |
| `decision-sheet` | 判断票を人が判断できる形で説明する（一括判断・グループ化を含む） |
| `apply-decision` | 判断の記録、台帳への反映、実物の直しまで |
| `export-excel` | Excelとレビュー表の出力 |
| `import-review` | 記入済みのレビュー表の取り込み |

### エージェント（役割）

役割を分ける目的は、**作った本人が自分の作業を確かめないこと**。どの係も「どれが正か」は決めない。

| エージェント | 役割 | 持たない権限 |
|---|---|---|
| `extractor`（抽出係） | 情報源からMDの材料を取り出す | 判断しない |
| `matcher`（照合係） | ずれを検出し、判断票を作る | 直さない |
| `applier`（反映係） | 判断どおりにMDや実物を直す | 判断の中身を変えない |
| `auditor`（監査係） | 反映後に、判断どおりか・新たなずれがないかを確認する | 直さない |

### スクリプト（決まった処理）

**事実を確定させる処理はすべてスクリプト、意味を判断する処理だけをAIに任せる。**
同じ入力から必ず同じ結果が出ること、全件を漏れなく比べること、量に強いこと、Claudeの外（CI）でも動くことが理由。

重要度の順：

1. 照合（構造の一致検査）— 判断票の信頼性の土台
2. IDの鎖の検査 — つながりの切れ、IDの重複、どのテストにも紐づかない要件
3. 抽出 — DB定義やテストコードなど機械的に読めるもの
4. Excelとレビュー表の入出力

## v0.1 の範囲

- 対象：**テーブル定義**（MD・Excel設計書、DDL〔H2・MySQL・PostgreSQL〕、JPA）と **テスト**（MDの仕様書・報告書、JUnit 5、surefire の実行結果）
- 一周：取り込み → 判断票 → 判断の記録 → 台帳への反映 → 実物の直し → 同期で解決 → Excel清書 → レビュー表 → 指摘の取り込み → 判断
- 規約の詳細は [spec.md](spec.md)
- spring-petclinic で試し、7テーブル・24列・18テストクラス・96テストから、75件のずれが判断票になった（設計書の範囲外のテーブル、JPAとDBの必須の食い違い、PostgreSQLだけの長さ無制限、報告書の「予測PASS」と実行結果のerrorなど）
